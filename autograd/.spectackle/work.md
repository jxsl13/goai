## T-01KYJR35K5E6FVTTCVDD9VSTBQ Accumulate gradients in place at fan-in, behind an explicit ownership set
kind: task
state: draft
created: 2026-07-27

SITE: autograd/autograd.go:263-275 (*Tape).accumulate, specifically :269 — sum, err := backend.Execute(t.exec, backend.OpAdd, []*tensor.Tensor{prev, g}, nil).

WHY HOT: called from accumulateGrads (:244) for every non-nil input gradient of every node, i.e. once per EDGE of the graph, and it takes the allocating branch at every FAN-OUT point — the QKV split (3-way fan-in on one activation), every residual stream, every weight-tied embedding, every parameter reused across timesteps.

MEASURED COST: BenchmarkSliceVJP_QKV_F32 ([32,128,2304] -> [32,128,768]) is 1,666,150 ns and 37,749,004 B/op; that 37.7 MB is the mandatory full-input-shaped zero dx at vjp_slice.go:26. A QKV split produces three of those, and the tape then runs TWO accumulate calls, each allocating and zeroing ANOTHER 37.7 MB and doing a 3-array pass over 9.4M elements (about 2.7 ms each at the measured AddF32 rate). So the accumulate half of QKV backward costs roughly as much as all three slice VJPs combined, per layer, per step.

DEFECT: prev and g are both dead after the statement, yet a third buffer is allocated to hold their sum. An in-place prev += g would halve the traffic and remove the GC pressure.

THE NAIVE FIX IS UNSAFE — this is the load-bearing part of the task and must not be skipped. bcastReduce returns its argument UNCHANGED when the shapes already match (vjp.go:62-64), and the OpAdd VJP returns bcastReduce(g, ...) for BOTH input slots (vjp.go:128). So for Execute(ctx, OpAdd, []*tensor.Tensor{x, x}), accumulateGrads calls accumulate(x, g) twice with the SAME POINTER, and on the second call prev == g. A naive in-place prev += g would double g in place — and g is t.grads[n.outputs[0]], still live for the downstream walk. That is a silent wrong-gradient bug. Additionally the seeded cotangent is stored by reference (autograd.go:135, documented at :118-121 as caller-owned), so mutating prev can corrupt user memory.

SAFE FIX: an explicit ownership set on the tape — owned map[*tensor.Tensor]bool, the gradient buffers the tape allocated and exclusively holds. In accumulate: if prev != g AND t.owned[prev], add in place (AddF32(prevSlice, prevSlice, gSlice) or an OpAddInto-style path) and keep t.grads[x] = prev; otherwise take today's allocating path and mark the RESULT owned, since the OpAdd output is freshly allocated by the kernel and referenced by nobody else. NEVER mark the seeded cotangent owned. This converts a k-way fan-in from k-1 allocations to 1.

CONSTRAINT COMPLIANCE, stated explicitly: this touches only the BACKWARD path (t.exec, autograd.go:32, a non-recording context). It does not touch Tape.Record or backend.Execute's recorder stripping (backend/execute.go:114-117), so the record-exactly-once property at the choke point is preserved by construction.

VALIDATION GATE (benchmark only): NO benchmark covers fan-in accumulation today — that coverage gap is itself worth noting. Write BenchmarkFanInAccumulate (x [32,128,2304] F32 on tape.Context(); three OpSlice ops forming the QKV split; sum the three; Backward on the scalar; fresh tape per iteration) and BenchmarkFanInAccumulateDeep ([256,256] F32, 8-way fan-out of one activation, depth 8) which isolates the per-fan-in FIXED cost from the per-element cost. Report allocs — the win shows as both ns/op and B/op.

EXPECTED: about 1.3-1.5x on the QKV fan-in benchmark and roughly -33% B/op on a 3-way fan-in, asymptotically -(k-1)/k. Medium confidence on the exact ratio (derived from measured SliceVJP_QKV plus measured AddF32 rates, not a direct A/B), high that the allocation count drops.

BIT-IDENTITY BAR: bit-identical — prev[i] += g[i] computes the same single rounded add in the same left-to-right order over fan-in edges, and the tape visits contributions in a fixed reverse-tape order that is unchanged. No reassociation, no widening. THE ENTIRE RISK IS ALIASING AND OWNERSHIP, NOT NUMERICS, which is why the ownership set is not optional. Required tests beyond the existing gradcheck suite: a targeted test for Execute(OpAdd, []{x, x}), and a BackwardGrad test with a caller-retained cotangent that asserts the caller's tensor is UNMODIFIED after the call.

PERFSCAN RULE, partial: an allocating binary op where both operands are dead and one is a same-shape accumulator field. AST shape: an assignment m[k] = f(m[k], v), or tmp := f(prev, v); m[k] = tmp where prev := m[k], in which f is a known allocating elementwise call, prev has no other use after the statement, and m is a map or slice field of the receiver. Worth adding, but the detector MUST emit a mandatory "prove exclusive ownership of the destination" warning, since that is precisely the part a static pass cannot check — as this task itself demonstrates.

## R-01KYMJRJFCFVVSM02RSXX1GHZP Six autograd VJP files have NO tolerance-0 gate — build the oracle before optimizing them
kind: research
state: draft
created: 2026-07-28

MACHINE-PRODUCED LIST, reproducible with internal/perfscan/tools/exactness_sweep.py from the repo root. The sweep perturbs every float store in a file by one ulp-scale factor, rebuilds, and runs the package suite; a file that stays green has no test sensitive to a 1-ulp change in that path.\n\nGATED (suite goes red): vjp.go, vjp_cumsum.go, vjp_elementwise.go.\nNOT GATED, 22 stores total: vjp_ia3.go (3), vjp_linalg.go (2), vjp_mla.go (6), vjp_moe.go (7), vjp_softcap.go (2), vjp_ssm.go (2).\n\nWHAT NOT-GATED MEANS, precisely, because it is easy to overread: NOT untested. A gradcheck with a finite-difference tolerance legitimately cannot resolve one ulp. It means there is no EXACT gate, so any rewrite of those paths that claims bit-identity cannot be verified without first building an oracle — a frozen copy of the pre-rewrite loop plus a tolerance-0 cross-reference. That is real work to be budgeted BEFORE the optimization, not discovered halfway through it.\n\nWHY THIS WAS MECHANIZED: two hot paths were rewritten in consecutive rounds before anyone noticed no test could see the change — broadcastVJP (vjp_reduce.go) and prodVJP. Both were caught only by probing coverage first rather than trusting a green suite. Two-for-two justified automating the check instead of remembering to do it.\n\nPS6001 FLAGS NONE OF THE SIX, AND THAT IS CORRECT, NOT A RULE DEFECT: they are SINGLE-path typed kernels, so there is no second arm that could disagree and nothing for a dual-path rule to demand a cross-reference against. The blind spot is structural — an exactness gate for a single-path kernel has to be a frozen oracle, which no static rule can conjure. Do not widen PS6001 to cover this; it would fire on every typed loop in the repo.\n\nACTION FOR A FUTURE OPTIMIZATION ROUND targeting any of the six: step one is the oracle and its mutation probe, step two is the benchmark, step three is the transform. Ordering matters — the two paths above were rewritten first and gated afterward, which is how a silent numerical regression would have shipped. Note also that vjp_softcap.go already carries a shipped optimization (the SoftCap VJP reciprocal-multiply, 1.28x/1.29x), so an exactness claim there is already load-bearing and unverified.\n\nThe sweep refuses to score a non-compiling or unmatched mutation as green (PROC-MUTATION-VALID-001) — that failure mode is what made an earlier hand-rolled harness report three false ungated results.
