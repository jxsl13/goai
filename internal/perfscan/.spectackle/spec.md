## PERF-ID-COLLISION-001
WHEN a new check ID is minted, the perfscan check registry SHALL reject any ID not verified free on main and in every open PR touching the registry, via `gh pr diff` per PR.

Rationale: Check IDs are documented as stable and are the handle used by //perfscan:ignore directives and -checks= selection. Two branches minting the same next-free ID collide silently: both build, both pass their own suite, and whichever merges second leaves one ID carrying two meanings, so an ignore directive written for one check suppresses the other. Observed when PR #394 (PS4004 scalar-copy-loop, PS6001 unverified-dual-path) and PRs #412/#413 independently minted PS4004 and PS6001 against a main that had neither; resolved by renumbering #412 to PS4007 and #413 to PS3004, both free in either merge order.

## PERF-SUPPRESS-INERT-001
WHEN a //perfscan:ignore directive is written, the a perfscan suppression SHALL re-run the scan and confirm the finding is gone; a directive that fails to apply is silently inert and reads as accepted.

## PROC-PROFILE-PARKED-001
IF a parallel program profiles as mostly runtime synchronization, or a known-serial function profiles as negligible, THEN the implementing agent SHALL read the GOMAXPROCS 1/4/12 curve to size the serial fraction, then profile at GOMAXPROCS=1 to locate it.

Rationale: Two directions of the same trap, both measured, and the second nearly cost a 2.14x win. FIRST, parked time inflates: a parallel program profiling as mostly runtime synchronization is not necessarily paying for it, and a spin-before-park replacement measured 2-4% slower. Scavenger time behaves the same way — runtime.madvise at 24.36% of samples in linalg.Lstsq dropped to 9.97% after a 39.7% allocation-count cut and moved the wall clock not at all at n>=512, because the scavenger runs concurrently. SECOND, and the inverse: serial work DEFLATES by roughly the core count, because it is one thread working while the rest park and are still sampled. After GMM eStep was fanned out, a GOMAXPROCS=12 profile showed pthread_cond_wait and _signal at 66% with mStep at 2.9%, reading as nothing left but scheduler overhead. The GOMAXPROCS curve contradicted it: 65.79ms at one core against 37.74ms at twelve, a plateau at 1.75x that is Amdahl for a 44% serial remainder. Profiling at GOMAXPROCS=1 put mStep at 37.4% flat, and fanning it out over components was worth another 53%, taking the whole benchmark to 3.69x and the scaling curve to 3.72x. A multi-core profile can neither be trusted to condemn synchronization nor to exonerate a serial function.

## PERF-CHECK-ADVICE-MUST-TRANSFER-001
WHEN a perfscan check states a remedy generalized from one measured site, the implementing agent SHALL re-measure that remedy on a site with the opposite memory-access shape before stating it unconditionally.

Rationale: PS1007 was generalized from a sparse P·V where the input was read d-STRIDED, and its remedy — strip-mine the inner loop by 4 with the outer loop innermost — was stated as the fix. Applied to linalg QR, where the input is already read as a CONTIGUOUS row slice, that remedy wins only at small sizes and then evaporates: LstsqMat -2.56% at n=64, -1.92% at 256, -0.52% at 512, indistinguishable from base at 768, because it trades one contiguous pass over the submatrix for n/4 strided passes whose cost grows with the outer trip count. The remedy that wins on the contiguous shape is the opposite move — unroll the OUTER loop by 2 with separate accumulating adds, keeping the inner pass contiguous while the accumulator lives in a register across the pair: -2.31% to -3.16% at every size, geomean -2.69%. Both forms are bit-identical, so only measurement could separate them. The check now carries both remedies plus the discriminator. The failure mode is specific: a check derived from one site encodes that site accidental access shape as if it were the pattern, and the only way to find the missing case is to run its own advice on a site that differs in exactly that respect.

## PROC-MUTATION-MAY-FIX-THE-CODE-001
WHEN a mutation of a detector clause reddens no floor, the implementing agent SHALL ask whether the clause is needed at all before writing a floor for it, since 1 of 3 such clauses was removable.

Rationale: Mutation testing is usually read as a verdict on the TESTS, and the reflex is to add a fixture. Three of six clauses in the PS6009 permutation classifier came back toothless and the diagnosis differed per clause. Two were genuinely missing floors, but with a specific cause worth naming: each fixture was already excluded by an EARLIER clause, so it could never isolate the later one — a floor must be constructed to pass every clause except the one under test. The third was not a test gap at all: the clause excluded the case where the outer and inner slice names match, which bought nothing (a direct s[i] < s[j] is already excluded by the nesting requirement, its index being a bare parameter) and actively harmed precision by skipping a real self-permutation s[s[a]], which has exactly the property the check exists to flag. Deleting the clause and adding a POSITIVE floor for the case it had wrongly excluded was the correct response. So a toothless mutation is a question about the predicate, not only about the fixture.

## PERF-NO-CHECK-FOR-JAM-REMAINDER-001
IF a scan rule is proposed for a jam whose remainder falls back to a per-item call, THEN the implementing agent SHALL decline it: 12 syntactic sites yielded 1 actionable, and the deciding ratio is not in the syntax.

Rationale: The GMM full-covariance kernel jams 4 components and handed k%4 to the scalar per-component path; adding a 2-wide step was worth 4.37% because that benchmark runs k=6, so a THIRD of the components took the unjammed path. Generalizing it looked mandatory, so the predicate was written and counted before any detector: a jam step for V+N <= LIMIT followed by a unit remainder for V < LIMIT whose body calls a helper. 12 sites repo-wide. Auditing each one collapsed the population. Most remainders call something cheap — math.Sqrt, f16ToF32, a tensor SetF64, or an Errorf error path — not the heavy per-item kernel the jam replaced. Only nn VQ Quantize matched structurally, and there the jam runs over BATCH ROWS inside parallelRows, so the remainder is at most 3 rows per worker: at batch 512 with 12 workers that is 36 of 512 rows, 7.0% unjammed against GMM 2 of 6 components, 33.3%. Those rows are merely unjammed rather than several times slower, putting the upside near 1 to 2 percent and requiring a 2-wide kernel to be written before it could even be measured. The quantity that decides the payoff is the remainder SHARE, N over LIMIT, and syntax cannot tell a configured component count of 6 from a data dimension of 512 — both are ints. Adding the check would emit 12 findings with one worth acting on and no way to rank them, which is what PERF-HOTNESS-IS-NOT-SYNTAX-001 forbids. The optimization stays recorded here and in the GMM commit instead of in a detector.

## PROC-MUTANT-MUST-NOT-CRASH-001
IF a mutation makes a detector panic instead of returning a different answer, THEN the implementing agent SHALL rewrite it to keep every operand live, since a crashing mutant reddened an unrelated fixture and proved nothing.

Rationale: Testing the slice-versus-array clause in PS2008 fixed-array exclusion, the obvious mutation deleted the at.Len == nil test — which left at.Len evaluated on a nil ast.ArrayType pointer for every non-array type. The mutant panicked, and the panic surfaced as a failure in TestPS2008Silent/scratch-not-stored, a fixture with no bearing on the clause. Read naively that looks like the clause is guarded; it is not, and the real floor was still missing. A mutation is only evidence when the mutant computes a DIFFERENT ANSWER over the same inputs, so it must keep every operand live and neutralize only the decision: at.Len == nil && false rather than removing the term. Two tells that a mutant is invalid rather than informative — a fixture unrelated to the clause turns red, or the whole package fails at once. The same episode also shows why a second slice fixture was needed: the existing one declared rows with an assignment and exercised the composite-literal branch, so the var-declaration branch had no floor at all.

## PERFSCAN-EVIDENCE-BELONGS-IN-THE-MESSAGE-001
IF a measurement is recorded for a perfscan check, THEN the implementing agent SHALL put it in the EMITTED MESSAGE, not only the registry line or the doc comment, since the message is what an agent triaging a finding reads.

Rationale: The tool keeps evidence in three places and no single one was complete, which made a whole audit wrong. Scanning the checks[] registry one-liners produced a list of eight checks supposedly carrying no measurement - PS5001, PS6016, PS6011, PS6017, PS4006, PS3002, PS6018, PS4011 - every one of which states its numbers in the emitted message. Re-running the audit against messages then showed the reverse failure: PS6008's AQLM 49-to-51MB versus GBM 64MB-to-2007MB contrast, the single fact that decides whether one of its 100 findings is free or a 31x regression, lived only in the detector's doc comment; PS6009's 3.11x and 1.50x allocation results likewise; and PS1005's own numbers had been added to the registry line one session earlier while its message still said nothing. A doc comment is read by whoever edits the detector, and the registry line by whoever runs -list. Neither is read by an agent triaging a finding. Fixed for PS1005, PS6008 and PS6009. Note that absence of a ratio is not always a gap - PS6004 is a correctness-risk check whose evidence is a count of four kernels found blind, and that belongs in its message exactly as written.

## PERFSCAN-AUDIT-A-NEW-CHECKS-FINDINGS-001
IF a newly added perfscan check reports findings, THEN the implementing agent SHALL audit every one before trusting the count: all 23 PS1009 sites already had the arm it asked for, leaving zero actionable and 23 permanent noise.

Rationale: PS1009 was written after measuring a real 6.46% win on nlp rows2D, whose Dtype() switch had an f64 arm and left f32 on the accessor. The check found 23 sites and that looked like 23 opportunities. Reading all 23 showed every one already covered both f64 and f32, and the only unconverted clause in each was the default - which holds f16, bf16 and the quantized dtypes, whose storage is u16 or packed and needs a genuine conversion rather than the exact widening that makes an f32 arm a one-liner. So the actionable count after fixing rows2D was zero, and the check as written would have emitted 23 findings forever. The narrowing suppresses a switch that covers F32 and leaves only default slow, while still firing on a NAMED case left on the accessor, because listing a dtype and not converting it is a choice rather than an accepted tail. The general lesson is that a predicate count sizes the SHAPE, not the opportunity: the shape was right and its instances were already finished. Auditing the findings of a check one has just written is cheap and is the only thing that separates the two. Same family as PERF-CHECK-EXISTS-BEFORE-ADDING-ONE-001, which asks whether an existing check already covers the class; this asks whether the codebase has already done the work.

## PERF-NO-CHECK-FOR-ROW-HOIST-001
IF a scan rule is proposed for hoisting a loop-invariant row out of an inner loop, THEN the implementing agent SHALL decline it and fold the advice into PS4006, whose narrower row-per-allocation predicate covers the actionable sites.

Rationale: The bare two-deep-index predicate matches 225 sites repo-wide (105 at depth 2, 99 at depth 3) with no hotness signal. One measured instance, randomOrthogonal at -21.3%, does not make 225 sites defects, and the compiler already hoists many of them.

## PROC-INTERSECT-FINDINGS-WITH-PROFILE-001
WHEN choosing which perfscan finding to spend time on, the implementing agent SHALL intersect the findings with a line-level profile first and work the overlap, treating the check list as a candidate generator rather than a ranking.

Rationale: In one sweep of five packages, 436 of 439 findings sat on lines carrying no measurable profile time, and the three that did were in files locked by open PRs. Every win this session came from the profile first and the check second; the tool is hotness-blind by design (PERF-HOTNESS-IS-NOT-SYNTAX-001). Caveat for whoever repeats this: pprof -lines -top reports only the hottest lines, so the overlap is understated, not zero.

## PERF-ROW-COUNT-DECIDES-STRIP-MINE-001
IF a contiguous-input accumulation loop is judged against PS1007 case (b) refusal to strip-mine, THEN the implementing agent SHALL count how many output rows the loop already accumulates together first, since four rows turn a strip-mine into a register tile that won 35 to 50 percent where one row lost.

Rationale: PS1007 case (b) was measured on a single-row rank-1 update (linalg QR) where strip-mining decayed to nothing by n=768. The portable GEMM bands hold four output rows, so strip-mining by 4 builds a 4x4 register tile: f32 -34.8% and f64 -50.5% geomean, growing with size. The separating quantity is arithmetic intensity, 16 FMAs per 8 loads versus 4 per 5.

## PROC-CHECK-THE-SCANNER-BEFORE-DERIVING-001
WHEN a defect class has been hit more than once and is about to be reasoned about from first principles, the implementing agent SHALL run the scanner for an existing check reporting that class first, since PS6023 had already flagged the stale threshold that was later re-derived by hand.

Rationale: matmulInlineWork appeared in PS6023 output as gemm.go:95 throughout the session while four thresholds went stale. It was found instead by reasoning about which constants the GEMM work invalidated, and the re-sweep then measured +37.26% at the gate value. The tool was right and unread.
