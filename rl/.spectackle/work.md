## T-01KYJQ799JEFMVTMH1GRWAAX65 Remove two redundant forward passes on the PPO rollout and DQN learn paths
kind: task
state: draft
created: 2026-07-27

Two independent defects in the same package, both pure dispatch waste on per-step paths, both with essentially zero numeric risk. Land as two commits, benchmark separately.

DEFECT 1 — PPO computes the critic one row at a time, per env step. SITE rl/ppo.go:258 in rlRollout (value stored at :265). PPO.Update (:161) -> rlRollout -> loop body runs RolloutSteps (default 256) times per Update. Each iteration does three dispatch clusters: actor forward (:246), OpSoftmax (:250), critic forward (:258); via nn.Linear.Forward each forward is 5 backend.Execute calls plus a fresh backend.NewContext(). So the rollout pays about 2800 dispatches on m=1 TENSORS per Update, versus about 400 dispatches on m=256 tensors in the entire update phase. At hidden=64 and obsDim<=16 that is pure overhead, not FLOPs. THE KEY OBSERVATION: the critic value is NOT USED DURING COLLECTION — it is only appended to ro.values and consumed after the loop by GAE (:170), and the critic's parameters are untouched inside rlRollout. So 256 batch-1 critic forwards produce a quantity that one batch-256 forward would give. (The actor call at :246 genuinely cannot be hoisted — its softmax feeds sampleAction which feeds env.Step.) FIX: drop the critic call from the loop; after collection do one forward(ctx, critic, ro.states) and fill ro.values from column 0. Prealloc the 7 parallel slices with make([]T, 0, steps) (currently about 9 realloc/copy rounds each). Hoist one ctx above the loop.

DEFECT 2 — DQN runs the identical online-net forward twice every step. SITE rl/rl.go:410 (qPred) and :434 (q), both inside (*DQN).learn, which (*DQN).Episode calls on EVERY environment step once the buffer reaches BatchSize. Both are forward(ctx, d.Net, states): same network, same input, NO parameter mutation between them (the only writes are target.SetF64 at :414-430). qPred exists solely to seed the non-taken entries of target so their MSE gradient is zero — and the taped q already holds those exact numbers. Per learn step that is 5 wasted Execute dispatches, one wasted Context and about 6 wasted intermediates, out of a step totaling roughly 3 forwards + 1 backward + 1 Adam. FIX: reorder — open the tape, run q first, build target reading q.AtF64(i, a) in place of qPred.AtF64(i, a), then nn.MSE(ctx, q, target). Reading AtF64 off a taped tensor records nothing and target stays a fresh non-taped tensor, so the graph is unchanged. Delete the :410 forward. While there, batch/states/nexts at :394-399 are three fresh allocations per step at fixed BatchSize — reusable agent-owned scratch.

VALIDATION GATE (benchmark only): neither is covered (rl has only BenchmarkRLForward and BenchmarkSoftUpdate). Write BenchmarkPPORollout (env NewChain(9,50), actor policyNet(9,64,2,1), critic Sequential(Linear(9,64), ReLU, Linear(64,1)), seeded PCG, b.ReportAllocs, calling rlRollout directly so the update path is excluded) plus BenchmarkPPOUpdate for the end-to-end share; and BenchmarkDQNLearn (prefill the replay buffer with 4096 transitions outside the timer, then time d.learn) so learn is isolated from env stepping and epsilon-greedy acting.

EXPECTED: PPO 30-45% off rlRollout and roughly 15-25% off PPO.Update at small net widths (shrinking as hidden grows and FLOPs start to dominate dispatch); DQN 12-20% off learn, scaling with BatchSize. High confidence on the rollout number, very high on the DQN redundancy being real, medium on the exact percentages.

CORRECTNESS BAR: BOTH ARE RNG-NEUTRAL, which is the thing to protect here. PPO: the critic consumes no random numbers and the actor forward, softmax and sampleAction stay in place in the same order, so the trajectory (actions, rewards, dones, logpOld) is bit-for-bit unchanged and TestPPODeterministic (ppo_test.go:297) is unaffected. The only values that could move are ro.values, and only if the m=1 GEMV path disagrees with the m=256 band path — the repo asserts these are bit-identical at tolerance 0, and on darwin/arm64 both go through the scalar band kernel, but VERIFY THAT ON-HOST with a tolerance-0 parity assertion before merging, since GAE feeds the policy gradient. DQN: values are bit-identical (Linear->ReLU->Linear, no dropout, no RNG) and the number and order of rng draws is untouched since only :396 consumes RNG and it stays first, so TestDQNLearnsChain seeded behavior is preserved exactly.

PERFSCAN RULES REQUIRED, two. (i) REDUNDANT PURE RECOMPUTE within a function body — within one FuncDecl, collect CallExprs that are syntactically equal after normalizing away a leading context/tape argument; report a pair when the callee is in a whitelist of known-pure entry points, every non-context argument ident is unassigned between the two sites, and no reachable state is written between them. No existing PS rule covers this, and it recurs anywhere a no-tape preview pass precedes the real taped pass. (ii) A REFINEMENT OF PS1003 rather than a new class: PS1003 already matches a single-element-batch call in a loop, but it fires on BOTH the actor and the critic here and only one is fixable. Add the predicate that makes it actionable — flag only when the result is loop-carried-independent, i.e. the result flows exclusively into an append to a slice declared outside the loop (or an indexed store) and never into a loop-body branch condition, another call argument, or the loop's iteration state. That hoistable-versus-not distinction is what turns PS1003 from noise into a fix.
