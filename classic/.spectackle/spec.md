## EST-002 {applies: go:classic_test.TestPredictWidthGuardConsistency}
IF a predict-family method receives a row whose width differs from the feature count recorded at Fit, THEN the estimator SHALL return a clean error naming the row index, the got width and the want width, never panicking and never silently truncating.

Rationale: Two live failure modes: LinearRegression.Predict ranged over the input row instead of its coefficients, so a three-feature model given two features silently returned a plausible wrong number with a nil error; SVC panicked with an index-out-of-range while gradient boosting silently mispredicted, because shallow splits still traverse the surviving features. The guard lives at one site per estimator and is proven non-vacuous by stripping it and confirming the test goes red. Migrated from cavekit SPEC.md V37.

## MIRROR-A-GATHERED-COLUMN-FEATURE-MAJOR-001
WHEN a loop reads one column of a [][]T at a data-dependent row, x[idx[k]][f], and the same column is re-read many times, the owner of that matrix SHALL mirror it feature-major once where it is already walked and read the mirror, accepting the n*d element memory cost and gating the change with a bit-exact digest.

Rationale: Measured on the GBM exact-split builder. The gather x[cf[start+k]][f] was 51 percent of scanFeatures and 16 percent of the whole classic package: every read is a pointer chase into a separate length-d row, so n reads touch n cache lines spread over the whole n*d matrix and use 8 bytes of each. Feature-major turns the same access into a scattered read inside ONE contiguous length-n array. BenchmarkGBMHist_exact_80k minus 19.5 percent, _20k minus 13.6 percent, GBMFit minus 25.4 percent, with ForestFit flat as a control, for plus 15.6 percent bytes at n=20000 d=20 - exactly the n times d float64 the mirror costs, a trade to state rather than hide. The mirror is a pure copy so nothing moves by a bit, which is why only a bit-exact digest can gate it: two mutations that changed x by one ulp and that flipped the partition test from <= to < left every digest untouched, because the model reads x only through comparisons against midpoints of DISTINCT adjacent values and its outputs are leaf means of y. Four mutations do redden it. Encoded as perfscan PS3057, narrowed to the data-dependent row form: the strided x[i][f] shape has the same orientation but the rows are visited in order at a fixed stride, and including it reported 118 sites tree-wide instead of 3.

## POOL-A-PER-WORK-ITEM-SCRATCH-SET-001
WHEN a type whose initializer allocates 3 or more buffers is constructed once per work item, the that initializer SHALL take the buffers from a sync.Pool, growing each only when the pooled one is too small, and return them when the item finishes.

Rationale: Measured on the CART builder inside a random forest fit, where initIdx allocated seven n-sized buffers per tree and was 32 percent of the fits allocated bytes. Pooling them plus the ascending index buffer: BenchmarkForestFit bytes 59.06 to 34.03 MB, minus 42.4 percent, allocations 2742 to 1798, minus 34.4 percent. TIME WAS FLAT - 111.2 to 108.0 ms, inside the run-to-run spread - because the fit is already parallel and was not allocation-bound. Report a change like this as a resource win or not at all. TreeFit and GBMFit were unchanged in both bytes and time as controls, TreeFit because a lone tree takes the presort branch and never calls the pooled initializer. THE SAFETY ARGUMENT WAS ALREADY MADE BY THE EXISTING CODE: each of these buffers was already reused across the thousands of nodes of ONE tree, which proves every one is written before it is read, and nothing distinguishes the first node of a new tree from the hundredth node of the old one. The one buffer that could not be pooled is the node slab, because the finished tree points into it. A table whose entries do not depend on the size - clogc[c] = c times ln c - is EXTENDED rather than rebuilt, so its O(n) log sweep is paid once per pool entry instead of once per tree. Encoded as perfscan PS3058, reported at the initializer rather than at a construction site because the construction usually sits in a function called per iteration and the tool builds no call graph.

## A-LOOP-OVER-AN-EXPENSIVE-CALL-HAS-DEPTH-ONE-001
WHEN looking for unused parallelism and the per-item work lives inside a CALLEE rather than in an inner loop, the reviewer SHALL check single loops too, because every nest-based check requires a depth of 2 or more and cannot see this shape.

Rationale: Measured on the RBF support-vector fit, which sklearn is on record as winning by 2.0x and which scaled at 1.02x on twelve cores. A serial profile put 40.6 percent of it in kernelCache.column, whose body is one loop of n independent kernel evaluations - depth 1, because the O(d) work is inside kernel() rather than in an inner loop. PS3034, PS3059 and PS3063 all require depth 2 or more and were all silent. Banding that loop and the cache diagonal: BenchmarkSVCFit/n4000_rbf 6.99 to 5.48 ms, minus 21.5 percent, and n1000 minus 9.3 percent, with the GBM fit flat as a control and the race detector clean. Bit-identical: each entry performs exactly the arithmetic it did before and only which goroutine performs it moves. EXPECT AMDAHL, NOT THE CORE COUNT - 6x on 40.6 percent of the work is 1.27x overall, and the SMO iteration the cache feeds is sequential by construction, so the remaining 60 percent is not reachable this way. The helper added for it sizes its worker count to the work rather than only gating on it, because the cache is called thousands of times per fit with a column only just above the gate, which is the one regime where that transform has measured a win. Encoded as perfscan PS3065, 18 candidates tree-wide, narrowed by requiring the callee to contain a loop of its own so an O(1) callee does not report.

## A-TIE-RULE-NEEDS-ITS-OWN-TEST-NOT-A-DIGEST-001
WHEN a serial reduction with a first-wins tie rule is replaced by a chunked parallel one, the test suite SHALL pin the tie rule with a fixture that MANUFACTURES a tie, in both placements, rather than relying on an output digest.

Rationale: The CART feature scan was fanned out over feature chunks, and its winner rule - visit features ascending, take a new best only on strict less-than, so the lowest index wins a tie - had to be reproduced by the chunked version in two places: within a chunk and in the fold across chunks. THE BIT-EXACT FOREST DIGEST DOES NOT COVER IT. Mutations flipping either strict less-than to less-or-equal left the digest green, because its data produces no exact-cost tie between different features. A direct fixture does: duplicate one feature so two columns give identical impurity at every cut, then assert the tree records the LOWER index. IT NEEDS TWO PLACEMENTS. With the twin ADJACENT both features land in one chunk and only the within-chunk comparison decides; with the twin at the LAST index they land in different chunks and only the fold decides. Each placement leaves the other mutation green. And the width matters: at eight features the worker count clamps to eight, every chunk holds exactly one feature, and the within-chunk rule has nothing to bite on at all.

## A-CHUNKED-BEST-OF-SCAN-FOLDS-IN-ORDER-001
WHEN a serial loop keeping a running best over independent items is chunked across workers, the implementer SHALL apply the same strict comparison within each chunk and then fold the chunks in ASCENDING order with that same comparison, so the serial winner is reproduced exactly including ties.

Rationale: First-wins survives both levels: if every chunk keeps the lowest-indexed of its own equals and the fold takes a new best only on strict less-than while walking chunks in order, the global winner is the lowest-indexed of all equals, which is what the serial loop produced. Measured on the CART feature scan, which ran at 1.01x on twelve cores: BenchmarkTreeFit 10.20 to 9.69 ms, minus 5.0 percent, with the forest fit flat as a control. Modest because a tree work sits in a few large nodes and the rest is below the fork gate. Encoded as perfscan PS3068, 29 candidates tree-wide. TWO THINGS THE CHECK NEEDED. A range over VALUES has an underscore for its index, and taking the index alone made the check silent on the very scan it was written from - for _, f := range feats. And the fan-out may be ONE CALL AWAY: applying the transform produces a caller that dispatches to a helper which fans out and contains no helper call itself, so the converted site reported until the suppression followed same-package callees. A residual false positive is recorded rather than fixed: a scan inside a function whose CALLER runs it in a band is already parallel and this check cannot see that direction.
