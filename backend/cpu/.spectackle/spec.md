## CPU-002
WHERE the f32-native GEMM path under the SIMD experiment build, the cpu backend SHALL be compared against the f64 reference at rel 2e-3 and abs 1e-4 rather than at tolerance 0.

Rationale: This path accumulates in f32, so it amends the general f64-accumulation rule; observed maximum deviation is about 1e-4 for K up to 128. The default build keeps scalar f64 accumulation and stays bit-exact, f64 is bit-exact in both builds, and convolution through the banded GEMM is untouched. Migrated from the worker spec Iw4 and ADR-01KYCZF2W8F3GS2X0410JSHPKZ.

## intent
- R-01KZ15RPY3E9DT1W3ZXXGDA8Q8 Round T1060: masked-MHA mixed-dtype panic fixed; the check for that class drafted and withheld: Consumed: the mixed-dtype panic fixed on both arms with a reference-parity gate, and the check for the class withheld with its two noise sources diagnosed (a guard split across an enclosing type switch, and outputs allocated from an input dtype). ## FANOUT-SIZING-PAYS-ONLY-AT-HIGH-CALL-FREQUENCY-001
IF a fan-out helper serves large operations called a few times rather than small ones called thousands of times, THEN the work-sizing transform of SIZE-THE-FANOUT-TO-THE-WORK-001 SHALL not be applied, because it measures neutral there and neutral is not a reason to add a knob.

Rationale: The transform that won on the quantized decode matmul - minus 4.1 percent wall and minus 27 percent system CPU - was applied to the two nn fan-out helpers and measured FLAT across three benchmarks with CPU flat too: HQQuantize 91.2 to 90.3 ms, KAN_256x256 11.99 to 11.91, TPAForward_1024 55.9 to 54.2, user CPU 25.7 to 26.1 s on both arms. Not shipped. What made decode different is CALL FREQUENCY AT NEAR-GATE WORK: thousands of calls per generation, each just above the threshold, so the wakeups dominated. MEASUREMENT DISCIPLINE MATTERS HERE MORE THAN USUAL: a first run at 10 iterations read as a 6 percent REGRESSION on one cell, and 20 iterations showed it was noise - separate the arms before believing either sign. TWO FURTHER NEGATIVES from the same round. The cpu backends worker pool ALREADY sizes itself, which is why perfscan PS3061 does not list it, and raising its per-worker floor made decode monotonically worse - 522, 529, 542 ms at 1<<15, 1<<16, 1<<17 - so its constants are at their optimum and should not be touched. And after the gguf fix, a decode profile still shows 92 percent of samples in pthread_cond_signal and pthread_cond_wait, but the wakeup path is runtime.startm, the Go schedulers own thread starting, not the pools barrier: the remaining lever on decode is FEWER AND LARGER OPERATIONS - kernel fusion - not more tuning of the existing helpers.

## AN-OP-WITH-NO-OPTIMIZED-KERNEL-IS-A-STANDING-GAP-001
WHEN an operation is registered in the reference backend and in no optimized one, the maintainer SHALL treat it as a standing performance gap, rank it by caller hotness, and gate any new kernel bit-for-bit against the reference rather than to a tolerance.

Rationale: OpCholesky had no cpu kernel at all, so every caller on the default backend ran the correctness implementation. A cpu kernel with ref arithmetic line for line, taking FOUR ROWS PER PASS so the pivot row is loaded once and four independent accumulator chains run instead of one, measured 21.1 to 7.0 ms at n=512, a 3.0x, with allocations 6 to 5 and bit-exact agreement with ref in both F64 and F32 across five sizes straddling the fan-out gate. THE FIRST ATTEMPT WAS SLOWER THAN REF. Fanning out the row update is the classical-factorization shape PS3040 describes and it lost, 24.1 ms against 22.0 with allocations going 6 to 878, because there are n columns and the fork is paid once per column for a row update that shrinks as the factorization proceeds. Arithmetic, not parallelism, was the lever - and that is now the second measurement saying so for this loop shape. GATE BIT-FOR-BIT, NOT TO A TOLERANCE: a tolerance test passes a blocked or reassociated version too, and once one kernel disagrees every cross-backend golden silently becomes a tolerance test. F32 is computed in float64 exactly as ref does and rounded once on the way out so the two agree in both dtypes rather than only in F64. Encoded as perfscan PS3062, which found 26 such ops tree-wide including OpTranspose, OpConcat, OpEmbed, OpSVD, OpEigh, OpQR and OpSolveSPD. NOTE THE MEASUREMENT TRAP: the existing logdet backward benchmark pins itself to the reference backend on purpose, so it does not move when a cpu kernel appears - a new benchmark on the default backend was needed to see this at all.

## BELOW-GATE-ARM-TESTS-THE-WORK-PER-WORKER-001
WHEN a kernel routes small inputs through a fan-out helper that would run them inline anyway, the kernel SHALL test the work against 2x the helpers PER-WORKER floor, not against its on/off threshold, and call the band body directly below that.

Rationale: Measured on the new cpu transpose kernel. The 512 by 64 shape - one attention heads K matrix, so the most common transpose in the tree - has exactly 32768 elements, which sits ON the backends parThreshold. The helper therefore considered splitting, computed one worker from the per-worker floor, and ran the body inline; the kernel had already paid for the closure, which escapes and is a heap allocation on every call. That alone made the new kernel 10 percent SLOWER than the reference it replaced, 26.0 against 23.6 microseconds, with 5 allocations against 4. Testing m times n against twice the per-worker floor and calling the band directly below it brought the small shape back to parity, 23.0 against 22.96 microseconds and 4 allocations, while keeping 1024 by 768 at 233 against 525 microseconds, a 2.2x. THE THRESHOLD AND THE PER-WORKER FLOOR ANSWER DIFFERENT QUESTIONS: the first says whether splitting is worth considering, the second says how many workers the work can actually feed, and only the second predicts whether the fan-out will happen. Folded into the PS3040 guidance beside the existing plain-duplicated-loop note.

## THE-WORKER-POOL-IS-CLOSED-AS-A-TUNING-TARGET-001
IF a profile shows most samples in the worker pools barrier, THEN the reader SHALL not sweep the pool constants again, because all four have been swept with controls and none pays.

Rationale: Four constants measured across three rounds, each with an unrelated control benchmark. The per-worker work floor: raising it made quantized decode monotonically worse, 522, 529 and 542 ms at 1<<15, 1<<16 and 1<<17. The dense-regime work ceiling: widening it 16-fold bought a batched ViT forward 6 percent at best and moved Swin and the nn controls not at all. The dense-regime time gap: widening it cost Swin 79 percent and the multi-token-attention forward 16 percent. Forcing every operation into the dense regime read as minus 12 percent on Swin twice and then produced a 2.5x outlier on ViT, which is what the pools own comment predicts - capping off the efficiency cluster was measured at plus 20 to 34 percent on bandwidth-bound elementwise ops. WHAT THE PROFILE ACTUALLY SAYS IS NOT A TUNING PROBLEM. A batched ViT forward burns 11.1x CPU to deliver 3.86x of speedup, with 82 percent of its samples in pthread_cond_wait and pthread_cond_signal against 7.8 percent in the GEMM. That is the same shape quantized decode showed, where the wakeup path resolves to runtime.startm rather than to the pools own barrier logic. The remaining lever is FEWER AND LARGER OPERATIONS - kernel fusion - and no constant in the pool reaches it. Folded into the PS3061 guidance so the next reader of that check does not start the sweep over.

## AN-UNBENCHMARKED-CROSSOVER-IS-NOT-A-TUNING-OPPORTUNITY-001
IF a size gate switches implementations at a value no benchmark in the repository runs near, THEN the that constant SHALL not be treated as tunable until a cell exists in its crossover region, because nothing can measure whether moving it helps or hurts.

Rationale: Found while working the PS3070 candidate list. mhaGemmMinSeq is 16 and gates the gemm-routed attention path in both the forward and the backward, which have genuinely different cost profiles - two matmuls per head against five - so it is a textbook shared-threshold split. Every MHA benchmark in the repository runs at sequence length 512 or 1024, thirty to sixty times the gate, so no measurement distinguishes any value of it and the split would be speculation. The decode path, which is the one that could be near the gate, has a query length of ONE and takes the scalar arm regardless. THE OTHER PS3070 CANDIDATE IS A DIFFERENT FALSE POSITIVE and is recorded with it: geluGradPdfMin is an underflow floor reused on two quantities, a correctness bound rather than a knob, and splitting it would buy nothing and risk the invariant. Both triage questions - is it a knob at all, is the crossover benchmarked - are now in the checks own message, because between them they account for every candidate it found in this repository. A scan-rule candidate list is a list of SHAPES, and the shape is not the finding.

## ARM64-EXACT-RELU-001 {applies: backend/cpu/elementwise.go,backend/cpu/relu_f32_arm64.go,backend/cpu/relu_f32_arm64.s}
WHEN F32 ReLU executes on arm64, the CPU backend SHALL use ordered comparison and select so positive values retain bits while negatives, NaNs, and both zero signs become +0.

## ARM64-EXACT-ABS-001 {applies: backend/cpu/elementwise.go,backend/cpu/abs_f32_arm64.go,backend/cpu/abs_f32_arm64.s}
WHEN F32 Abs executes on arm64, the CPU backend SHALL clear the sign bit, preserve finite, infinity, and NaN payload bits, and set the F32 quiet bit on every NaN so the result is bit-identical to float32(math.Abs(float64(x))).

Rationale: M2 emits FCVT F32-to-F64, FABS, then FCVT F64-to-F32 for the incumbent expression. Raw-bit probes show that this clears signs and quiets signaling NaNs while preserving payloads; a plain vector FABS or sign mask would change the contract.

## ARM64-EXACT-NEG-001 {applies: go:cpu.negKernelCPU}
WHEN F32 Neg executes on arm64, the CPU backend SHALL toggle only bit 31 of every input lane so outputBits equals inputBits XOR 0x80000000 for all elements.
